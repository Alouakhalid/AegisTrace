How it works

From a git URL to a reviewable patch

Five deterministic stages. Every one of them leaves a row in the evidence vault that a reviewer can audit line by line.

Stage 01

Scope & manifest

The URL is validated, the repository is cloned at a pinned commit and every allowed host is recorded in a signed scope manifest.

Stage 02

Architecture extraction

An AST pass recovers routes, path parameters, ORM models and the invariants those routes imply. Tests and examples are excluded.

Stage 03

Hypothesis formulation

Routes and invariants are correlated into testable, prioritised hypotheses and paired with multi-identity probe plans.

Stage 04

Exploit & reproduce

Each plan is replayed against the running target as two identities, with database state snapshots hashed between runs.

Stage 05

Verdict & patch

Only three reproductions with a state mutation earn CONFIRMED. Verified findings get a patch on a branch and a human approval.

# CodeIntelligenceAgent · AST extraction routes 24 models 17 invariants 14 def patch_order( order_id: int, db: Session, ) # route + owner invariant recovered PATCH /api/v1/orders/{order_id} auth_required = True owner_field = order.user_id # excluded: tests/ and examples/ are not deployed code

The AST is the source of truth

Routes, ORM models and security invariants are extracted from syntax, not guessed from filenames. Handler functions, path parameters and the query layer all end up in a graph the agents can reason over.

  • Real HTTP methods and path parameters per route
  • ORM schemas recovered from the model layer
  • Ownership invariants derived per resource route
  • Test and example trees excluded, so counts stay honest

Two identities, three runs, one verdict

A hypothesis is not a finding until it is exploited. The dynamic stage replays the same request as the owner and as an attacker, diffs the database state, and the verification stage only issues CONFIRMED after three reproductions with state-mutation evidence attached.

  • Identity-bound probes per hypothesis
  • State snapshots hashed into the evidence chain
  • Rejected hypotheses kept as rejected, never deleted
  • Source-only scans stay UNCONFIRMED — that is the honest answer

Evidence

A vault your auditors can open

Every byte AegisTrace asserts is stored in an append-only SQLite vault with immutability triggers. Findings reference the hypothesis, the endpoint, the invariant and the exact evidence that proved them.

Immutable by construction

Evidence rows and state snapshots reject updates and deletes at the database level, not in application code.

Timestamped chain

Correlation ids, agent runs and task messages keep a continuous trail from request to verdict.

Reproducible verdicts

Each confirmed finding stores the request, the response, the identity used and the state delta it produced.

Full audit export

Machine-readable findings, patches and approvals, ready for a compliance review or a ticket system.

Scoped credentials

Role-bound identities are declared per engagement, and secrets never enter a log line or an artefact.

Auditable patches

Remediation lands on its own branch with a diff and a commit, and waits for a human decision.

The questions engineers actually ask

Three separate reproductions of the same exploit against a running target, each one producing an observable state mutation, with the request, the response and the state snapshot attached to the finding. Anything short of that is recorded as UNCONFIRMED. A scan of source code with no running target will never manufacture a confirmation.

For static work, no — it clones the repository and reads the AST. To confirm an access-control flaw it needs a reachable target, which you can point at locally with web_target_url. Without one, AegisTrace still derives real routes, models and invariants, and honestly labels every result as unconfirmed.

Python is the primary target: FastAPI, Flask, Django, SQLAlchemy and SQLModel are all parsed down to route level, and any Python web framework with standard decorators is covered. When a repository has no server-side routes at all, AegisTrace reports zero rather than inventing some.

The remediation agent writes the fix on a dedicated fix/aegistrace-* branch, commits it with a diff, and raises an approval request. Nothing merges into your working branch on its own — a human accepts or rejects it in the Approval Center.

A scan clones into a separate cache directory and is read-only against your checkout. The only writes are the remediation branch, and only after a finding is confirmed in the sandbox.

Evidence rows and state snapshots are protected by database-level immutability triggers: update and delete statements are rejected by SQLite itself. Findings reference the exact hypothesis, endpoint, invariant and evidence identifiers that produced them, so the whole chain can be replayed.
